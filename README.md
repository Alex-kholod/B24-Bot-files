# B24 Docs Bot

Чат-бот открытых линий Битрикс24: складывает документы, которые клиент присылает в чат,
в чек-лист задачи этого клиента. Если подходящей задачи нет — создаёт новую и запоминает
её идентификатор, чтобы следующие документы того же клиента попадали туда без повторного
поиска. Работает молча: в чат ничего не пишет, только ведёт лог и очередь повторных попыток
на случай временных сбоев Битрикс24.

Дизайн-документ: `docs/superpowers/specs/2026-08-31-b24-ol-docs-bot-design.md` (каталог
`docs/` не входит в репозиторий — см. `.gitignore` — и доступен только тем, у кого есть
рабочая копия с историей разработки).

## Требования

- PHP 8.4 или 8.5 (`composer.json` требует `"php": "8.4.* || 8.5.*"` — это ограничение
  идёт от `bitrix24/b24phpsdk` v3).
- Расширения PHP: `curl`, `intl`, `json`, `pdo_sqlite`.
- Публичный HTTPS-домен, на котором будут доступны `install.php` и `handler.php`.
- Портал Битрикс24 на коммерческом тарифе — REST API и открытые линии недоступны на
  бесплатном тарифе.

## Установка на сервере

```bash
git clone <адрес репозитория> b24-docs-bot
cd b24-docs-bot
composer install --no-dev
cp config.php.example config.php
```

Откройте `config.php` и заполните значения:

| Ключ | Что вписать |
|---|---|
| `client_id`, `client_secret` | выдаются при создании локального приложения (раздел ниже) |
| `oauth_server_url` | `https://oauth.bitrix24.tech/` для порталов `.bitrix24.ru`, `https://oauth.bitrix.info/` для `.bitrix24.com`; пустая строка — риск, см. предупреждение ниже |
| `scope` | оставить как в примере — обе области нужны одновременно (см. ниже) |
| `bot_code` | код бота, уникальный на портале |
| `bot_name` | имя, которое клиент увидит в списке участников чата |
| `bot_token` | произвольная строка до 40 символов, секрет бота |
| `handler_url` | `https://<ваш-домен>/handler.php` |
| `default_responsible_id` | ID пользователя-ответственного по умолчанию (если у CRM-сущности не назначен ответственный) |
| `task_group_id` | ID группы, в которой создавать задачи, `0` — без группы |
| `checklist_title` | заголовок корневого пункта чек-листа |
| `max_attempts` | сколько раз повторять отправку файла, прежде чем пометить `failed` |
| `db_path` | путь к файлу SQLite (по умолчанию `var/data/bot.sqlite`) |
| `log_path` | каталог для логов (по умолчанию `var/log`) |
| `log_level` | уровень логирования Monolog (`info`, `debug` и т. д.) |

Дайте веб-серверу и cron-пользователю права на запись в каталог `var/` (там лежат SQLite
и логи):

```bash
mkdir -p var/data var/log
chown -R www-data:www-data var
```

Примените миграции базы:

```bash
php bin/migrate.php
```

Команда печатает число применённых миграций и создаёт файл `var/data/bot.sqlite`
со всеми таблицами (`auth_tokens`, `task_links`, `processed_messages`, `pending_files`,
`settings`), если его ещё нет.

## Настройка веб-сервера

Корень сайта — каталог `public/`. Каталоги `src/`, `bin/`, `var/`, `vendor/` не должны
быть доступны по HTTP: за пределами `public/` в них нет смысла отдавать ничего наружу,
а `var/` дополнительно содержит базу и логи.

Пример блока для nginx:

```nginx
server {
    listen 443 ssl;
    server_name example.org;

    root /var/www/b24-docs-bot/public;
    index install.php;

    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.4-fpm.sock;
        fastcgi_index install.php;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }

    location ~ ^/(src|bin|var|vendor|config\.php)(/|$) {
        deny all;
        return 404;
    }
}
```

На боевом сервере в `php.ini` (или в пуле FPM) выставьте:

```ini
display_errors = Off
log_errors = On
```

Оба HTTP-входа (`install.php`, `handler.php`) сами перехватывают исключения и отвечают
клиенту без вывода трассировки, а ошибку пишут в лог. Но если `display_errors` включён
на уровне PHP, при неперехваченной ошибке (например, синтаксической или фатальной на
раннем этапе, до входа в try/catch) PHP допечатает трассировку прямо в тело ответа —
а это публичный эндпоинт, который слушает весь интернет.

## Создание локального приложения

В административной панели портала откройте **Разработчикам → Другое → Локальное
приложение** и создайте серверное приложение:

- **URL приложения**: `https://<ваш-домен>/install.php`
- **URL пути установки**: `https://<ваш-домен>/install.php`
- **Права доступа (scope)**: `imbot,imopenlines,im,task,tasks,crm,disk,user`

Про `scope`: в нём одновременно нужны `task` и `tasks`. `task` — это старые методы
`task.checklistitem.*`, которыми бот пишет в чек-лист. `tasks` — область REST 3.0,
нужная для `tasks.task.file.attach`, которым бот прикладывает файл к задаче в режиме
без ATTACHMENTS (см. раздел «Диагностика»). Один без другого работать не будет —
если кто-то решит «упростить» строку до одного значения, бот сломается в рантайме без
явной ошибки при установке.

После сохранения приложения Битрикс24 выдаст `client_id` и `client_secret` — впишите
их в `config.php`.

Откройте `https://<ваш-домен>/install.php` из карточки приложения в портале (кнопка
«Установить»/«Настройки»). Страница сохранит токены портала, зарегистрирует бота через
`imbot.v2.Bot.register` и покажет его идентификатор. Если что-то пошло не так на втором
шаге (токены уже сохранены, а регистрация бота — нет), страница это укажет; исправьте
причину и выполните на сервере:

```bash
php bin/install_bot.php
```

Эта команда идемпотентна — `imbot.v2.Bot.register` по коду бота вернёт существующего
бота, если он уже зарегистрирован.

## Подключение бота к открытой линии

**Это обязательный ручной шаг, и его нельзя сделать кодом.** Регистрация бота (описанная
выше) не подключает его ни к одной открытой линии — это отдельная настройка каждой линии.

Откройте **Контакт-центр → открытые линии → нужная линия → Обработчики / Аналитика и
обработка** и подключите зарегистрированного бота как обработчика линии. Без этого шага
приложение выглядит полностью установленным и работоспособным, но бот не получит ни
одного события — сообщения от клиентов просто не будут до него доходить, и никакой
ошибки нигде не появится.

## Крон

Файлы, которые не удалось обработать сразу (временная ошибка Битрикс24, недоступность
диска и т. п.), попадают в очередь `pending_files` и обрабатываются повторно с задержкой.
Поставьте в crontab:

```cron
*/5 * * * * php /path/to/b24-docs-bot/bin/retry.php
```

Команда без флагов забирает из очереди файлы, у которых наступило время повторной
попытки (`status = 'new' AND next_attempt_at <= now`), и пытается обработать их ещё раз.

## Диагностика

```bash
php bin/selftest.php
```

Проверяет по порядку: конфигурация читается и содержит обязательные ключи → в базе есть
сохранённые токены портала (иначе установка не завершена) → бот доступен через
`imbot.v2.Bot.register` → текущий режим записи вложений в чек-лист → сводку по очереди
`pending_files` (сколько файлов в работе, обработано, с ошибкой).

Логи лежат в каталоге из `log_path` (по умолчанию `var/log`), формат — Monolog, уровень
задаётся `log_level`. В логах никогда не должно быть `access_token`, `refresh_token`,
`application_token`, `bot_token` или содержимого файлов — редактирующий процессор
вырезает эти значения перед записью.

Настройка `checklist_attachments_supported` (таблица `settings`) хранит, поддерживает ли
конкретный портал вложения в `task.checklistitem.add` через параметр `ATTACHMENTS`. Бот
проверяет это один раз — на первом же документе — и запоминает результат:

- **режим 1 (поддерживается)**: файл прикладывается прямо к пункту чек-листа;
- **режим 0 (не поддерживается)**: файл прикладывается к самой задаче
  (`tasks.task.file.attach`), а в текст пункта чек-листа добавляется ссылка на скачивание.

Поэтому нормально, если на одних порталах файлы лежат внутри пунктов чек-листа, а на
других — прикреплены к задаче со ссылкой в тексте пункта: это не баг, а разница между
версиями Битрикс24. Чтобы заново определить режим (например, после обновления портала),
сбросьте сохранённое значение:

```bash
php bin/selftest.php --recheck-attachments
```

Статусы строк в очереди `pending_files`:

- `new` — ожидает следующей попытки (изначальной или повторной);
- `done` — файл успешно записан в чек-лист;
- `failed` — исчерпано число попыток (`max_attempts` из конфигурации).

Чтобы вернуть зависшие с ошибкой файлы в очередь на новую попытку:

```bash
php bin/retry.php --failed
```

Это сбрасывает у всех строк со статусом `failed` счётчик попыток и статус `new`, а затем
`retry.php` в этом же запуске сразу пытается их обработать.

## Разработка

```bash
composer test
```

Тесты лежат в `tests/` и повторяют структуру `src/`. Юнит-тесты не должны ходить в сеть:
обращения к Битрикс24 подменяются фейком (`tests/Bitrix/FakeB24Api.php`), а не реальным
HTTP-клиентом.
